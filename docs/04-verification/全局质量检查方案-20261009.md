# 全局质量检查方案

日期：2026-10-09。范围：当前一期业务、正式B/C前端、后端模块、AI网关、数据库设计与迁移、工程文档和测试。目标是查清不一致与实际缺陷，再按影响修复；不以测试数量、截图或模拟通过替代真实业务验收。

依据：[ADR-011](../03-architecture/ADR-011-一期业务收口与交付边界.md)、[一期未完成事项](../01-development/一期未完成事项.md)、后续ADR及用户最新决定。原始母版和历史资料保留，历史决定不直接当成当前缺陷。执行分四部分，逐部分交付结果，不一次混改所有模块。

## 第一部分：建立基线与检查范围

盘点当前业务规则、正式路由、接口、数据库、运行服务、未完成项和测试入口，形成“业务能力—实现—测试—证据”对应关系。区分正式页面与原型、当前规则与历史记录、模拟与真实运行。重点确认旧测试到底覆盖哪一版页面，以及是否有新能力未进入集中回归。

交付：检查范围、测试分类、覆盖缺口和当前版本基线。完成条件：每个主要业务模块知道查什么、用哪份规则、有哪些测试及哪些尚不能证明。

## 第二部分：检查业务、代码、接口与文档的一致性

按身份/组织、赛事/发布、报名/队伍、收费/退款、现场/结果、通知/隐私、AI/双端交互逐组核对。追踪从页面到接口、授权、状态和事务，再到数据约束与文档；优先越权、丢数据、金额/名额错误、重复执行、时间边界和任务恢复。核对数据库设计源、生成物及已应用迁移，禁止重写已应用迁移。

交付：统一问题清单，标明规则来源、影响、代码位置、复现方式和优先级。已授权规则下的明确BUG直接修复；业务规则尚未决定的事项单独列出，不擅自改变权利。完成条件：重点流程已追踪，实际BUG、文档错误、测试错误和未实现能力分开记录。

## 第三部分：核对测试有效性并校准

逐项核对测试是否调用真实业务函数、是否使用当前接口字段/状态/权限，以及前端选择器和流程是否对应新版页面。检查只断言截图/文案、未知请求被默认成功、跳过失败、强制点击遮挡按钮、模拟数据自证等问题。用关键反例核对断言是否能发现真实错误；按风险补测试，避免照抄实现或为每个简单按钮增加测试。

交付：测试适配清单、修复后的测试、关键缺口及入口映射。完成条件：相关测试与当前代码对应，能说明保护了什么，以及不能证明什么；旧原型测试保留为原型测试，不冒充正式产品回归。

## 第四部分：分层回归、验证修复并收口

依次执行静态/文档检查、前后端编译与单测、正式B/C页面和AI交互、隔离数据库与匿名HTTP，再办理可执行的普通角色业务验收。数据库测试只在专用临时库，模拟写入不得进入真实业务；真实角色与外部短信/支付等缺少环境或资质时明确记录阻塞，不绕过约束。

交付：可复现运行结果、修复与复验记录、剩余问题和下一轮顺序。完成条件：本轮问题都有状态和证据，修复项复验通过，失败/未执行/外部阻塞没有包装成通过；TC01—TC80仅有符合条件的真实证据才更新状态。

## 执行方式与进度

按上述四部分顺序推进。每部分给一次简明结果：发现什么、改了什么、验证怎样、下一部分查什么。问题优先级按业务影响排序：越权/资金/数据完整性，核心流程阻断，状态与失败恢复，文档和体验一致性。发现问题时保留复现证据，再决定修复；不为增加通过数量降低断言。

### 第一部分初步盘点

以下为方案制定时的首轮记录。后续正式执行的当前结果以[第一部分报告](全局质量检查-第一部分-20261009.md)为准，不把两次运行的结果混为一轮。

| 测试入口 | 实际用途 | 当前判断 |
| --- | --- | --- |
| Test-BusinessUi / Test-ConsumerUi | 正式B/C页面、导航、状态展示及响应式；授权接口主要为隔离样例 | 可验证新页面是否能跑，但不能证明真实接口与事务；本轮复跑 |
| Test-AiBusinessUi / Test-AiConsumerUi | 新版正式助手的提示词、发送、收起、恢复、来源和授权请求 | 新版已有专门测试；此前38/58项是隔离交互，不等于全部业务验收 |
| Test-CriticalUi / Vitest | 资金/邀请关键写交互、登录回跳、时间和请求防重 | 须在第三部分逐条对照当前业务实现与新版布局 |
| Test-UiPrototype / Test-AiUiPrototype / Test-AiConsumerPrototype | 静态设计原型 | 保留设计回归用途，不能当正式Vue页面适配证据 |

| Test-CriticalDatabase / Test-CriticalHttp | 临时PostgreSQL约束/锁、匿名拒绝与HTTP | 与真实业务服务并发/完整角色链路仍有差距 |
| Test-BackendHttp / Test-GeneratorHttp | 框架、生成器及可选MCP烟测 | 前者要求特定本地条件；不可为了检查正式产品而随意关闭验证码/开启MCP |
| Test-CriticalRisks集中入口 | 既有关键风险组合 | 未包含新增AI助手与AI网关测试，不能据此宣称所有模块全量通过 |
| check-source.py | 已冻结迁移、API模块依赖、共享表排除、部分文档链接及80验收记录 | 不验证全部文档语义或全部业务实现；现有文档链接检查仅覆盖部分目录 |

需后续校准的证据边界：部分浏览器夹具对未登记GET返回成功空数据，可能遮住接口路径/字段变化；现有AI创建测试的talk夹具主要返回update，尚未充分覆盖真正CREATED、重复确认和失败恢复。两项都是待核对的测试缺口，不直接认定生产业务已经出错。

### 第一部分执行结果

实际复跑Test-BusinessUi：116项/34张截图通过；Test-ConsumerUi：99项/44张截图通过。它们运行当前5173正式Vue页面，已能适配当前首页、导航和主要手动业务页面。范围主要是隔离接口下的显示/导航/响应式和状态解释，不能据此保证全部后端接口匹配。此前新版助手专测38/58项不在本轮重复计入。

check-source通过；全目录本地文档目标检查0失效。没有真实业务写入，没有修改验收JSON。证据.local/global-audit-b-ui.log、.local/global-audit-c-ui.log、.local/global-audit-baseline.json、.local/global-audit-doc-links.json。

当前能够回答：前端测试并非全部停留在旧页面，正式B/C主要页面测试确实能运行新版；但“测试代码是否全面匹配业务代码”尚不能下结论。集中入口遗漏AI、默认GET成功夹具、缺少AI真实创建状态回归、模块级测试分布不均和默认跳测，都需要第二、三部分核对和校准。第二至第四部分尚未执行，不因本轮215项页面检查通过而标为完成。
