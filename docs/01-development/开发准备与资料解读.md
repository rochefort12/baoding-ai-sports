## 2. 当前范围

产品目标是以保定为试点的城市体育综合服务平台，长期保留赛事 OS、场馆 OS、用户 OS。当前完整展开赛事组建、报名、比赛执行和长期档案，覆盖尽量广的运动目录及规则族。

本期主链：承办账号注册、组织资质人工审核及授权 → 赛事结构、规则与资源准备 → 审核发布 → 身份与队伍选择 → 预报名占位、材料及费用办理 → 有效名单 → 自动抽签与约束编排 → 报到与单场阵容 → 比赛结果确认 → 晋级、排名、申诉及纠错 → 成绩与荣誉档案、通知、退款和归档。

首期采用 Web 与 H5，共享业务身份和状态。小程序后续接续。产品内 AI、商业场馆预约、约战、培训、票务、商城及文旅交易属于后续独立建设方向。自动抽签、编排、晋级和排名属于本期确定性竞赛能力。

母版记录 2026-10-08 为内部交付目标，正式交付日期未定。日期不证明产能或完成程度；排期需在核验代码资产和环境后形成。

## 4. 数据与状态设计的约束

以下是应保留的业务意义，具体表结构和实现方式仍待工程设计。

1. **身份分离**：账号、现实参赛人、提交人、当前办理人、监护人、实际付款人不是同一个对象。手机号、微信昵称或同名不能代替现实身份。
2. **组织授权**：平台共享身份与长期队伍可复用；组织只能读取其赛事合法授权的资料。联合主办署名不自动产生报名材料或财务权限。
3. **名单分层**：长期队伍成员、某赛事报名名单、某场比赛阵容分别维护。退队不自动退赛，换队长不改变历史付款人，新成员不继承历史个人冠军。
4. **规则与快照**：报名引用适用的规则、费用、名单及身份资料版本。当前资料或赛事配置更新不能静默改写历史事实。
5. **状态分离**：报名办理、名额、资格审核、费用义务、收款、退款、场次、成绩及荣誉分别建模。已付款不等于资格通过，退赛批准不等于已退款。
6. **名额守恒**：赛事去重人数与项目的人／对／队容量独立。跨项目取消只释放独有占用；重复提交、超时重试和并发争抢不得形成超卖或残缺的半对报名。
7. **资金关联**：计价单位、付款承担方式和收款路径独立配置。截图是待核实证据；退款按真实付款映射处理，累计退款不能超过对应可退余额。
8. **时间一致性**：只校验本平台内安排，区分赛事窗口、具体场次及潜在晋级。父子安排不能自冲突；未报名的队伍成员不能被全队锁定。
9. **竞赛可解释**：抽签可复核，人工调整执行同样约束。资源不足或规则冲突需明确未排原因；不得通过忽略硬约束凑出赛程。
10. **结果传播**：成绩更正需识别晋级、后续场次、排名、证书、荣誉和通知。已实际进行的比赛进入专业裁定，保留现实事实。
11. **材料与儿童边界**：监护、健康、证件、财务凭据和公开内容按用途授权。邀请入队、监护同意、报名代办与公开展示同意不能互相替代。
12. **通知与恢复**：发送、送达、已读、业务确认和协调完成分别记录。备份恢复还需核对外部已发生的付款、通知和比赛。

## 7. 开发接续顺序建议

以下是工程工作顺序建议，未锁定技术版本，也不降低母版的完整范围。

1. 核验开发工具、候选框架、许可证、数据库适配及部署条件，记录选型依据和实际版本。
2. 将业务对象、独立状态、授权范围和版本关系转化为可审查的数据模型、模块边界及接口契约。
3. 建立隔离种子与模拟环境，补齐 SD00—SD18 的可重置场景；明确模拟短信、支付、身份和资质服务的标识。
4. 先提供身份、组织授权、运动规则、长期队伍和资源的最小稳定切片，逐步打通报名、名额、费用、审核和名单。
5. 接续跨赛事日历、自动抽签编排、现场执行、晋级排名、申诉纠错、档案与通知，覆盖不同规则族。
6. 按 TC01—TC80 建立需求与实际证据映射，补做真实渠道、权限、资金、容量、恢复、旧系统切换及运营接管验证。

验收先关注名额守恒、重复操作、付款退款映射、跨租户拒绝、真实人员冲突、规则及名单版本、结果更正影响。单次页面演示、算法生成成功或样例清单存在，均不作为业务通过证据。
