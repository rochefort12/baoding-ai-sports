# 本地全 Docker 运行（2026-10-13）

Java 后端、Node 网关、Nginx 前端、PostgreSQL、Redis、MinIO 已实际在 Docker 中运行。用户最终选择新基线空库，重新注册和准备业务数据；明确无需旧库兼容或旧库到新库迁移。架构见 [ADR-046](../03-architecture/ADR-046-本地全Docker试运行与数据副本.md)，基线依据 [ADR-047](../03-architecture/ADR-047-业务迁移基线合并.md)，Flyway最终入口依据 [ADR-049](../03-architecture/ADR-049-Spring-Boot集成Flyway.md)。本地测试就绪不等于生产部署或业务验收完成。

## 访问入口

| 用途 | 入口 |

| 参赛者登录／注册 | http://localhost:5193/portal/login ／ http://localhost:5193/portal/register |
| 工作账号／平台管理 | http://localhost:5193/login |

平台初始账号为 `admin`，随机密码保存在本机忽略文件 `.local/docker-stack/platform-admin.json`，不使用上游公开默认密码；框架自带的用户2演示账号停用。该账号用于平台配置，不能代替参赛者或普通组织账号验收。MinIO 凭据在私有 `runtime.env` 中，不在公共文档或终端输出。参赛者账号须重新注册，原演示密码不适用于新库。

入口只向本机开放，后端和网关无宿主发布端口。手机／其他电脑不能用这里的 localhost 访问；LAN 测试需要单独配置监听及文件地址。

## 启停与构建

Docker Desktop 使用 Linux 容器。Windows 宿主终端和编排脚本使用 PowerShell 7；Linux Dockerfile 内使用原生 Maven、Java、Node、pnpm 和 apt，没有 PowerShell 依赖。

项目根目录执行：

```powershell
# 首次或修改代码后：初始化新基线、构建并测试镜像、启动、执行就绪检查。
./scripts/Start-DockerStack.ps1 -Build

# 日常启动：复用数据库、文件和应用镜像，不重置数据。
./scripts/Start-DockerStack.ps1

# 仅构建指定镜像。
./scripts/Build-DockerImages.ps1 -Services backend

# 只核对当前迁移，不启动应用。
./scripts/Apply-DockerMigrations.ps1 -Command validate

# 检查运行、代理、登录、私有文件存取和权限边界。
./scripts/Test-DockerStack.ps1

# 停止全部六个常驻服务，保留卷和数据。
./scripts/Stop-DockerStack.ps1
```

全栈使用 `docker-compose.full.yml`，六个容器为 `aisports-dev-docker-postgres/redis/minio/backend/ai-gateway/frontend`。资源不与原基础设施 Compose 或其他工作目录容器混用。只读应用根目录、非 root 用户、移除应用 Linux capabilities、禁止提升权限、有限日志轮转和临时目录。

前端采用多阶段构建后的 Nginx 静态资源，`/prod-api` 同源代理至后端，SSE 不缓冲，访问日志不记录查询参数。前端锁文件与原 `pnpm-workspace.yaml` 一起复制，冻结安装不变。Java17/Maven3.9.12、Node24/pnpm11.19.0；中文字体用于 Java 文档／图片生成。

## 新基线与文件

当前库是 `aisports_docker_fresh`，首次先在新库事务初始化框架／工作流表，再准备无 DDL 权限的应用角色。按照最新ADR-049，业务V001—V003由Spring Boot启动早期的Flyway专用所有者连接执行；业务连接池仍用受限的 `aisports_app`。迁移SQL从仓库根构建上下文复制到镜像，并原样打包在 `classpath:db/migration`。独立Flyway11.7.2容器仅用于框架版本0标记和手动检查／维护。

实际发现框架初始化后的 public schema 非空，Flyway直接 migrate 会拒绝。入口因此只在本脚本创建、框架已就位且尚无任何 `asp_*` 表／Flyway账本的新库，显式记录版本0的 `framework-only-initialization` 标记，随后由后端完整执行V001/V002/V003；不开启baselineOnMigrate，不跳过业务基线。此标记不用于接管旧业务库。已初始化后启动自动校验／应用后续版本。V003 收回业务账号对账本的权限。运行就绪后再执行约束验证与独立validate。

约束验证使用 `database/verification/preparation.sql`，临时数据全部 ROLLBACK。新库只包含框架及业务目录初始配置，没有旧参赛者、组织、赛事、报名、收款或成绩。MinIO 使用新的私有桶 `aisports-docker-fresh`，内网 endpoint 为 `minio:9000`，浏览器签名 endpoint 为 `http://127.0.0.1:29000`；附件不设公开读写。Redis 为本套独立容器，重新登录。

早期曾导出原 V038 试用库、核对118表摘要并恢复至 `aisports_docker_trial`，在副本执行过当时 V039—V041；这是最终空库选择前的历史步骤，已不在启动路径中。原生库、旧 Docker 副本、导出包和旧 MinIO 文件仍保留，当前应用不连接它们，不提供向新基线迁移的兼容路径。旧复制桶与新私有桶独立。

平台能力默认按渠道控制。可通过 `Enable-DockerTrialUI.ps1` 在当前就绪检查通过后，核对本机原已验证UI清单与运行中的定义 hash，只有完全一致的UI定义才通过平台发布接口配置；变化或未验证定义保留关闭，Agent渠道不开放。这只是本地试用配置，不继承旧业务事实，也不把旧普通角色验收算成本轮Docker业务通过。全新检出没有私有验收清单时不自动发布，需在平台能力管理按实际验证配置。

最终本机配置为55项UI能力开放；`honor.resolve`（荣誉审核）定义已变化，仍关闭，须针对当前定义验证后再发布。Agent渠道保持关闭。当前注册、组织申请、办赛及报名对应的已验UI定义已配置，不创建任何业务样本。

## 私有配置

`.local/docker-stack/runtime.env` 保存编排配置；`backend.env` 和 `gateway.env` 由入口按白名单生成。Java为Flyway专用连接接收所有者配置，业务数据源仍使用应用账号；网关不接收任何数据库、Redis、JWT、短信和MinIO凭据。模型及短信沿既有私有配置，真正从页面调用时遵循供应商计费；本轮技术检查未调用模型、未发送短信、未制造报名或资金事实。

构建上下文排除 `.local`、私有环境文件、依赖目录和旧构建产物。初始化状态、密码、日志、测试回执都保存在忽略目录，不提交。
