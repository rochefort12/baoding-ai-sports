## 1. 任务与范围

用户先要求客观评价两个本机页面，随后要求「将这些意见写入一个文档中，让另一个会话来执行」。本任务将评审意见落实到现有 HTML 原型，交付可查看的改版及验证证据。

- C 端：`http://127.0.0.1:5188/#home`。
- B 端：`http://127.0.0.1:5188/business.html`。
- 主要源码：`docs/05-ui/prototype/platform.js`、`consumer.js`、`business.js`、`common.js`、`styles.css`。验证入口：`scripts/Test-UiPrototype.ps1`。
- 保持同一项目、现有页面和品牌方向，保留原型数据标记；可调整共用组件，但回归受影响的办赛申请、赛事详情及其他原型页。
- 本轮不要求迁移正式 plus-ui、不修改后端、数据库或真实资金/通知，不扩张业务。正式接入仍由既有一期清单管理。

执行前先读项目 AGENTS.md、docs/README.md、最新交接、ADR-011、ADR-012、UI README及相关页面地图/状态矩阵。其他会话已补充办赛申请及准入原型，须保留其新内容，不用旧评审快照覆盖当前源码。

## 2. 评审结论与必须保留的优点

两端已有统一视觉方向。C 端偏品牌展示，具体赛事偏低；B 端状态表达清楚，但首屏布局和待办路径影响办理效率。以下观察来自真实浏览器渲染及部分交互，不是完整用户研究。

保留：深绿/浅绿/暖橙视觉关系；通用运动与保定城市元素；明确的赛事入口；未来服务的未开放标记；发布、举办、时间阶段的独立状态；资格、付款声明、有效实收及退款的分别展示；报名详情集中资金操作；organize/payment 权限分别控制；抽屉对话框语义及键盘焦点循环。遵守 ADR-011，不为了文案简化改变业务含义。

### P2：完成基础可用性与一致性

| 编号 | 实际问题 | 修改目标与验收 |
| --- | --- | --- |
| UI-R04 | C 端桌面导航、宣传按钮及快捷区重复提供发现赛事/我的运动 | 合并或降低一组重复入口的优先级。保留清楚的赛事主入口、个人报名入口及我要办赛，保留已有申请链路；避免重复移除后路径更长 |
| UI-R05 | 桌面「我的运动」、手机「运动」及「我的」语义边界不直观 | 核对各目标页职责后统一桌面/手机用语。例如报名与参赛记录入口可称「我的参赛」，账号档案称「我的」；最终名称由执行者结合现有内容确定，并同步页标题。不得虚构个人运动记录功能 |
| UI-R06 | 城市宣传卡手机独立占较大篇幅，辅助文字普遍较小 | 移除/压缩/融入手机城市宣传卡；保留城市辨识。手机重要说明/元信息建议不小于12px，正文优先14px，装饰标签可更小但不承载必要信息。先减字再增字号，检查长文案、底栏遮挡及对比度 |
| UI-R07 | B 端资金条件满足、补足实收、冻结依据等术语阅读负担较重 | 用简短任务标签，详细业务条件放辅助说明/提示；例如待审核、待核对收款。不能把声明写成到账、把审核通过写成已付款，不能隐藏整单计费、退款边界及禁止原因 |
| UI-R08 | 从资金待办进入长抽屉，需先经过报名依据及审核区才能到资金按钮 | 从付款待办选择报名后定位资金区域；从审核待办进入定位审核区域。保留同一详情及名单上下文、焦点顺序和独立权限。键盘用户能到达目标，避免滚动后目标被固定栏遮挡 |
| UI-R09 | 抽屉 Escape 不关闭；B 端名单页刷新回概览 | 补 Escape 关闭及焦点返回。嵌套弹窗时先关闭顶层弹窗，不能同时关掉抽屉。用 hash/路由或等价方式保留 B 端页/标签/必要筛选，刷新及前进后退可恢复合法视图；无效参数安全回退，不持久化敏感材料 |
| UI-R10 | B 端未来业务空间排在高频赛事操作之前 | 降低未开放场馆/生活服务入口优先级，例如下移到规划分组。保持通用平台扩展结构及清楚的未开放标记，不创建实际业务/权限或删除已有赛事功能 |

### P3：审美取向，仅作为参考

当前视觉温和克制，适合城市运动和社区赛事；竞技力量感相对弱属于主观风格判断。本任务不要求改品牌、换配色或重画全部插画。优先完成 P1/P2，再做小幅一致性优化；如准备改变整体风格，提出具体方案供用户评审。
