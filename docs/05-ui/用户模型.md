# AISports 用户模型

版本：V0.3。日期：2026-10-07。状态：一期目标设计，尚未进行用户访谈或可用性验证，不表示能力已实现。

## 1. 依据与使用方法

本模型依据 [ADR-011](../03-architecture/ADR-011-一期业务收口与交付边界.md)、对应[业务流程](../README.md)及 [B/C Page Map](README.md)。适用范围为指定组织羽毛球 M1 受控试运行。

这里的用户模型按任务、授权和关系划分，不构造虚假的年龄、职业、消费水平或访谈故事。下表“任务和边界”来自已确认业务；“界面需求”是待验证的设计判断。成年人和未成年人均独立注册、维护本人档案，不设置监护代办角色。

角色不是独立账号类型。同一自然人可以参赛、当队长及为一个或多个获授权组织办赛；办赛身份下还可以兼任审核、资金和现场人员。切换身份不会扩大权限。

## 2. 任务角色

| ID | 任务角色 | 已确认任务和边界 | 界面需求（设计判断） | 主要页面 |
| --- | --- | --- | --- | --- |
| U01 | 运动服务浏览者/赛事发现者 | 无需登录看通用平台入口及公开可见赛事；未来场馆/生活服务目前仅看方向，不访问名单和私人信息 | 快速判断报名窗口、是否收费、是否可报名；取消信息明确 | C00、C01、C02、C03 |
| U02 | 独立参赛者/个人提交人 | 独立平台账号注册/登录，报名需要时完善本人档案，填写本人赛事字段，提交报名、付款声明、合法整单撤回；查看本人报名、正式赛果和私人证明 | 看清下一步与阻碍；分辨声明、实收、审核和参赛资格；历史不被当前档案覆盖 | C03–C08、C13–C15 |
| U03 | 受邀参赛成员 | 识别赛事和邀请，本人填/确认字段；可见授权整单费用进度和本人正式结果；不是默认的付款办理人 | 明确本人尚需完成什么；确认不等于报名已正式提交或已经通过 | C09、C06、C07、C13–C15 |
| U04 | 长期队员/当前队长 | 处理入队与成员关系；当前队长代表队伍选名单、发起报名、办理付款声明与合法整单撤回；不得替成员确认敏感值 | 区分队伍成员与本次参赛名单，查看成员完成情况；转让后显示当前可操作职责 | C10–C12、C06–C09 |
| U05 | 办赛申请人/组织办赛人员 | 提交平台办赛申请；通过获得组织授权；本组织赛事、项目、字段、公开和取消办理 | 从申请进度进入组织；工作区显示赛事阶段、缺项和待办；恢复公开与首次发布区分 | C16、B16、B17、B01–B06、B14、B15 |
| U06 | 组织报名审核人员 | 以 organize 授权查看本组织赛事报名和用途允许的字段；收费足额才能人工通过；人工拒绝需业务理由 | 列表区分待成员确认、待实收、待审核、窗口已结束；详情展示冻结依据和阻断原因 | B07、B08 |
| U07 | 组织资金办理人员 | 以 payment 授权登记平台外真实收款、补款、冲正及退款；不凭付款声明确认到账；不可跨报名抵扣 | 同一报名内追踪义务、净有效实收与退款；填写真实人/金额/时间；异常有明确人工处理路径 | B08、B09 |
| U08 | 组织现场/结果人员 | 按 organize 等实际动作权限报到、手工建场次、录分/确认及有依据授奖；取消停止新执行，结束允许限定收尾 | 快速定位名单与场次；已报到和已确认事实醒目；付款异常区分未执行与已有执行 | B10–B12 |
| U09 | 平台办赛准入审批人员 | 超级管理员按提交版本批准/拒绝组织申请；certified 仅代表办赛准入，不逐场审批 | 查看提交版本和拒绝理由；批准后真实开户结果统一反馈 | P01、P02 |
| U10 | 平台账号核验/受理人员 | 经用途授权受理注销、重复身份关联及误关联修复；检查硬约束、留轻量依据；不是正常注销审批流 | 先看办理阻碍与授权范围；误关联先限制访问，再受控处理；必要摘要避免泄露敏感全文 | P05、P06 |
| U11 | 第三方实际付款人 | 可未注册且非参赛者；实际收退款必须核对此人；付款不产生参赛、队伍或后台权限 | 从提交人获得准确付款指引；通过已公开联系渠道处理核对，不新增第三方账号门户 | C08 的指引及 B09 的事实记录；无独立页面 |

U06/U07/U08 是组织工作的动作分工，不要求三个独立人员或新增三套角色体系。U09 的审批权限不自动授予 U10 的敏感身份处理权限，也不允许普通组织访问平台核验材料。

## 3. 对象与授权模型

| 对象/动作 | 本人/成员/队长 | 组织人员 | 平台人员与公共范围 |
| --- | --- | --- | --- |
| 当前基础档案 | 本人维护；验证手机号只读；改档不改旧报名 | 不因办赛身份获得全平台档案访问 | P05 仅经授权查轻量变更摘要；公开不见私人资料 |
| 本次成员答案 | 各人本人填写确认；队长看完成情况，不能代确认敏感值 | 按本组织本赛事审核用途访问必要值 | 无平台通用字段审批；不自动共享其他赛事答案 |
| 正式名单与资格 | 本人查看相关报名；提交人/当前队长办合法整单撤回 | organize 按冻结版本审核和执行 | 下架不剥夺已有关联访问；取消保留历史 |
| 付款声明 | 仅个人提交人/当前队长办理；普通成员看义务与进度 | payment 核对；声明不是到账 | 第三方付款不取得报名访问权 |
| 实收/退款 | 按本人授权范围查看；不默认全员可见完整付款人明细 | payment 办理；organize 不自动包含资金权限 | 非本组织禁止；收款接收人不随队长转让改变 |
| 正式结果/私人证明 | 本人所参与的已确认结果；双打各成员可看本单；私人证明各自可见 | 本赛事授权人员按职责管理 | 公开不展示私人证明；队长无权查看队员私人证明 |
| 取消消息 | 固定接收账号读取本人通知与业务跳转 | 授权人员看本赛事投递及受控重试 | 只用当前验证手机号发短信，不用第三方付款/紧急联系人号码 |
| 注销/身份异常 | 平台反馈渠道发起；先解决有效报名、资金、队长/唯一管理员等阻碍 | 组织协助处理自己职责内事项，不代办身份关联 | 用途授权核验；同号新注册不自动继承旧身份/职责 |

服务端始终校验对象、组织、关系、用途及动作权限。按钮可见性只是交互提示；组织切换、旧链接和并发变化后必须重新核验。

## 4. 设计假设与验证方向

下列是假设，不影响已确认规则，也不能作为真实用户研究结论。

| 假设 | 首版设计选择 | 后续用真实普通角色验证什么 |
| --- | --- | --- |
| 参赛者最关心“还能否报名”和“是否取得资格” | C02 清楚显示窗口/费用；C07 首屏显示资格、下一步和资金进度 | 能否解释“声明已付款但仍待到账/审核”；能否找对下一步 |
| 队长易混淆队员名单与本次名单 | C11 队伍管理与 C06 参赛成员分开，显示本人确认完成情况 | 能否发现未确认成员；是否误以为队长能代确认或退队等于退赛 |
| 办赛人员需要按赛事完成连续办理 | B03 工作区聚合项目、报名、现场、通知；B09 位于报名详情 | 能否从待审核定位资金缺口，而非在多菜单之间反复查找 |
| 多重身份易误操作其他组织 | 顶栏持续显示身份与组织，切换后重载授权和消息上下文 | 能否识别当前组织；旧异步结果/旧链接是否误显示其他上下文 |
| 人工资金操作易把计划当事实 | 表单明确实际付款人、发生时间、金额；退款计划与实际累计分别展示 | 能否区分待处理、部分退款、已退款；是否误用默认值确认到账 |
| C 端可能在移动设备使用，B 端可能需密集表格 | C 端先考虑窄屏任务流程；B 端表格保留必要列和详情入口 | 用实际使用设备检验可读性和操作；不先声称设备比例/使用频率 |

## 5. 平台扩展与用户假设

用户确认 AI运动不止赛事报名运营；场馆运营、本地运动撮合和体育信息是长期方向。当前 U01 可以从平台首页理解这些方向，但不能把预告算已可使用。未来场馆运营者、内容提供方、服务双方等任务角色待具体规则确认后建模；不将 U05–U08 的赛事授权直接复制到新业务，不编造用户研究。详见[平台级 UI 信息架构](平台级UI信息架构.md)。

## 6. 给后续 AI 设计的约束

AI 生成线框/页面时，以 [User Journey](User-Journey.md) 的任务顺序和[页面状态矩阵](页面状态矩阵.md)的阻断条件为输入，同时引用稳定 Page ID。不得新增监护代报、自动支付/退款、材料或付款截图上传、自动排赛/发奖、完整财务/工单和平台通用字段目录。

演示人物和数据标为虚构，不用真实证件/电话/健康信息。成功页必须说明成功的是提交、实收登记、资格通过还是退款记录；不能用同一个“完成”代表所有事实。当前资料没有用户访谈证据，之后可根据实际观察调整布局和文案；改变业务权利再与用户确认。

## 办赛申请人的界面补充

U05 的准入前任务使用平台账号：C16 为发现入口，B16 填写/保存/提交，B17 查看进度、拒绝理由与历史，再以获授权组织身份进入 B02。没有参赛档案或尚无组织授权都不阻止申请；准入前不得办理赛事/资金。U09 超级管理员沿 RuoYi 的 P01/P02，管理员视觉页本轮暂不画，不改变审核权。


平台账号入口不限定参赛者：队长与办赛负责人复用同一手机号账号；管理员独立若依入口。C00 为访客和普通平台登录默认首页，原任务优先，见[登录与导航决定](登录与导航设计决定.md)。
