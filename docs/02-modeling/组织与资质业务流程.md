# 组织与资质业务流程

日期：2026-10-06。状态：已开发，待业务验收。依据 ADR-004。平台账号、开户和管理会话以 [ADR-005](../03-architecture/ADR-005-平台账号与租户主体.md) 为准。

最新跨模块补齐见 [ADR-011](../03-architecture/ADR-011-一期业务收口与交付边界.md)：组织维护自有赛事字段目录；责任主体固定所属组织、赛事联系人确认公开并冻结；唯一管理人注销先移交、关闭相关办赛访问；资金/审核权限分开和顶栏身份切换。新增部分尚待实现/验收，短信服务旧查询错误是历史记录，不能以模拟注册代替正式开放接入。

本文确定 M1.2 的字段、状态、模块和外部限制。模型已写入 `database/model/catalog.py`，并由 `scripts/generate-model.py` 同步。库结构用 V007 变更，已应用的 V001–V006 不改写。

参赛者注册和本人档案仍以 [参赛者身份业务流程](参赛者身份业务流程.md) 为准。

## 1. 谁在用

注册完成的用户只有一种。同一个登录可以建自己的参赛档案，也可以申请一个组织。

| 关系 | 表 | 本期怎么出现 |
| --- | --- | --- |
| 平台账号 | `asp_account` | 自然人身份。`person_id` 可空。`backend_user_id` 只留作当前登录的遗留列 |
| 参赛档案 | `asp_person` | 用户自己在身份档案里保存。办赛申请不要求档案已齐 |
| 组织申请 | `asp_organization_application` | 用户登录后从「我要办赛」创建。平台级数据，没有业务租户 |
| 组织 | `asp_organization` | 只有申请通过后才创建，并带上新租户 |
| 组织成员 | `asp_staff_grant` | 通过时写给首次申请用户。这是进入组织的权威，不保存 `sys_user` |
| 租户主体 | `account_tenant_principal`、`sys_user` | 通过时按 ADR-005 开通。映射存在不等于已经授权 |

超级管理员使用若依原有管理员，留在管理租户。他只审核，不替用户保存或提交申请。

登录确认「你是谁」。本期用户最多一个组织，进入办赛时直接使用这个组织，不让用户选择租户或组织。以后如果一人多组织，再在登录之后选择组织。

## 2. 注册和「我要办赛」

注册页、手机号、阿里云验证码 2.0、本地短信验证码和密码规则都不改。不增加「参赛 / 办赛」选择。

登录后仍可进入 `/portal/identity`。页面上另有「我要办赛」：

- 没有申请时，打开一份空草稿。
- 草稿、待审或已拒绝时，打开这一份申请。
- 已通过时，看到组织已开放办赛。本期没有发布赛事的按钮。

本期一个用户只有一份组织申请。已有申请时不能再创建第二份。同名组织可以各自存在，不合并，也不按主体标识判重。

普通用户用手机号登录时不选择租户。登录号是 `platform_user:{asp_account.id}`，Token 带 ADR-005 的技术租户。技术租户和新开通的组织租户都不出现在登录列表里。未登录的租户列表仍可能在域名对不上时退回其余租户。

## 3. 申请上收什么

| 页面项 | 提交时 | 保存 |
| --- | --- | --- |
| 名称 | 必填，最长 200 | 明文。通过后抄入 `asp_organization.name` |
| 联系人 | 必填，最长 100 | 明文。可以和登录用户不同 |
| 联系方式 | 必填，最长 50 | 加密保存。不要求是手机号，不发送短信 |
| 附件 | 可空，可以多个 | 每个文件写入已有的 `asp_file`。版本只保存文件编号 |
| 申请说明 | 可空，最长 1000 | 明文 |

草稿可以缺项。提交时名称、联系人、联系方式必须都有。

附件的上传者是申请人。`asp_file.owning_tenant_id` 在通过前为空；通过后写成该组织的租户。文件不提供永久公开地址。开发环境把文件内容落在本地磁盘，不新开云存储。更换附件时不删除旧文件。

不采集主体类型、主体标识，不上传规定种类的执照，不做工商或公安核验。

## 4. 状态和历史

申请状态只有 `draft`、`pending`、`approved`、`rejected`。

1. 第一次保存为 `draft`。草稿不产生历史版本。
2. 提交后为 `pending`，并冻结第 1 版。待审期间不能改这一版。
3. 通过后申请为 `approved`。这一版保持通过时的内容和附件。
4. 拒绝时填写理由，申请为 `rejected`。这一版保持被拒绝时的内容和附件。
5. 拒绝后可以修改当前申请。未再次提交前，当前状态仍是 `rejected`。再次提交新增下一版，当前状态变为 `pending`。旧版不改。

历史放在 `asp_organization_application_version`。每一版有自己的名称、联系人、联系方式、申请说明、文件编号、状态、审核人和理由。审核人是超级管理员的 `sys_user` 编号。

其他人调用通过或拒绝时，服务直接拒绝。只隐藏按钮不够。

## 5. 通过后创建组织和租户

申请保持 `pending`，在同一个数据库事务里按这个顺序开通。失败则整笔回滚，申请仍是 `pending`。

1. 复用若依开户，只把管理员的产生换成该平台账号的租户主体。返回租户、部门、角色和 `sys_user` 编号。细节见 ADR-005。组织表的 `tenant_id` 不能为空，所以先拿到租户号。
2. 插入 `asp_organization`，`tenant_id` 使用开户返回的租户号。状态写 `certified`，表示平台已准入、已开放办赛。它不是资质审核通过，也不是主体验真。`current_qualification_id` 留空。不插入 `asp_qualification`。联系方式抄入 `contact_cipher`。`subject_type` 和 `subject_hash` 留空。
3. 写入 `asp_account_tenant_principal`。
4. 插入 `asp_staff_grant`：组织范围、`event_id` 为空、状态 `active`、动作同时有 `organize` 和 `payment`、生效时间为审核时间、截止时间为空。`account_id` 是申请人的 `asp_account`。报名审核用 `organize`，确认到账用 `payment`。
5. 把该版附件的 `owning_tenant_id` 写成组织租户。
6. 最后把申请改为 `approved`，并记下 `organization_id` 和组织租户编号。

一期这一份授权投影为该租户的管理员角色。一个租户对应多个组织时，不能再这样投影。读取组织数据时只进入这个租户。

`asp_organization.subject_type` 和 `subject_hash` 已由 V007 改为可空。本期不填假的信用代码。有摘要时仍按「租户 + 摘要」唯一；空摘要不互相占用。

组织状态在本期只有创建时的 `certified`。申请被拒绝时还没有组织行。`correction`、`expired`、`restricted` 留在模型里，本期不使用。

`OrganizationQualificationApi.isCertified` 只看组织是否为 `certified`。这里的「已认证」在代码名上沿用旧称，业务含义仍是平台准入，不是资质审核。`hasStaffAction` 只看有效成员授权里是否有该动作。两者在通过并写好授权之前都是否。

## 6. 平台治理和组织管理

平台治理就是超级管理员审核。使用若依超级管理员身份，不新造可以分配给别人的审核角色。

组织管理是用户和组织的成员关系，数据上可以以后分给其他人。本期只给首次申请用户写初始授权，没有邀请、添加用户或分配动作的页面。

## 7. 若依租户拦截

租户拦截器会改写没有被排除的表。查询、修改和删除自动加上当前登录租户。插入语句里若没有 `tenant_id`，拦截器会补上当前登录租户。插入填充只补创建人、部门和时间。

组织申请和申请版本没有 `tenant_id` 列，并写入 `application.yml` 的 `tenant.excludes`，与 `asp_person`、`asp_file` 相同。拦截器不改写这两张表。服务按申请人或超级管理员限制可见范围。

组织、成员授权仍是租户表。写入时放在新租户的上下文里，或在插入列中带上新租户编号。

## 8. 模块

| 位置 | 本期 |
| --- | --- |
| 注册 | 不改 |
| `ruoyi-sports-identity` | 增加「当前登录用户的平台账号编号」。不建参赛档案，不改本人档案 |
| `ruoyi-sports-organization` | 新建。申请、历史版本、通过、拒绝、创建租户和组织、初始成员都在这里。手写，不用生成器覆盖 |
| `aisports-api` | 身份模块实现账号编号查询。组织模块实现已有的 `isCertified`、`hasStaffAction`。通过和拒绝不做成其他模块的写接口 |
| `plus-ui` | 用户页的「我要办赛」，超级管理员的审核页。计划路径 `/portal/organization` 和 `/sports/organization-review` |

组织模块不引用身份模块的 Mapper 或实体。`PersonApi` 仍只回答当前登录本人且必填身份已齐。

## 9. 本期不做

- 注册时分成两个账号或两个租户。
- 一人多个组织、一个租户多个组织、加入已有组织。
- 把成员授权分给其他用户。
- 补正、到期、停用、复核、更换主体。
- 主体真实性、办赛资质认证，以及为此采集证件或执照类型。
- 属性目录。发布赛事、报名、收费、录分和证书不在本流程，见已开发的后续暂停点。
- 微信登录、手机一键登录、真实短信。
- 体育局门户。
- 用超级管理员演示用户的草稿和提交。

TC01 在本流程只覆盖「尚未 `certified` 就不能办赛」这一判断。赛事草稿和公开报名见后续已开发的暂停点。TC02 的到期、TC03 的跨组织授权、TC04 的联合办赛都不做。这些 TC 保持待业务验收。

## 10. 后期可选项

入口和页面可以以后拆开。下面几项改变的是能力，不改变「一个用户、一份参赛档案、组织成员是关系」：

- 主体真实性验证。
- 办赛资质认证，那时才使用 `asp_qualification`，并可以有补正和到期。
- 组织内分发成员和动作。
- 登录后切换组织。一人可以对应多个组织；一个租户也可以对应多个组织。
- 真实短信。它高于微信登录和手机一键登录，但不是本段的开发内容。

## 11. 外部限制

| 事项 | 和本期的关系 |
| --- | --- |
| 阿里云短信未开通，查询结果为 `isv.PRODUCT_UN_SUBSCRIPT` | 注册继续本机回显验证码。组织审核不依赖短信签名 |
| 验证码 2.0 场景 `test_ai_sports`（`8rbagstp`），本地不调用验签 | 注册沿用。不新申请场景 |
| 云存储未作为本期条件 | 附件落本地磁盘，编号进 `asp_file` |
| 真实证照清单未批准 | 附件由申请人自定，不规定营业执照 |
| 登录接口可能列出全部租户 | 开发时收紧未登录列表，组织租户不出现 |
| 组织表的主体类型和主体摘要 | V007 已改为可空。创建组织时留空 |

密钥和 AccessKey 只放在未跟踪的环境文件里，不写入文档、日志和交接。
