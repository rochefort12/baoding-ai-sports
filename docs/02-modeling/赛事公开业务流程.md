# 赛事公开业务流程

日期：2026-10-06。状态：已开发，待业务验收。依据 ADR-006。组织准入以 [ADR-004](../03-architecture/ADR-004-组织与资质.md) 为准。

本次同步已确认目标，新增规则未实现/验收，跨模块边界见 [ADR-011](../03-architecture/ADR-011-一期业务收口与交付边界.md)。

本文确定 M1.3 的状态、公开字段和查询方式。模型已写入 `database/model/catalog.py`，并由 `scripts/generate-model.py` 同步。库结构用 V008 变更。已应用的更早迁移不改写。

## 1. 谁在用

| 角色 | 本期能做 |
| --- | --- |
| 组织管理员 | 已进入该组织的管理会话，并持有 `organize` 授权。创建、编辑、发布、下架、重新发布、取消都用这一项授权，不另造角色 |
| 平台访问者 | 查看当前可见的公开赛事和详情。未登录也可以看。鉴权不在本模块另做一套账号 |
| 超级管理员 | 不审核赛事发布。治理性强制下架不在 M1.3 |

赛事属于组织。创建人只记在审计字段里，赛事不归个人。页面不向访问者展示租户。

## 2. `certified` 的含义

`asp_organization.status = certified` 只表示平台已准入、已开放办赛。

它不表示主体已验真，不表示办赛资质已审核，也不对应一份 `asp_qualification`。M1.2 通过申请时写入这个状态，本期没有把它改成其他状态的操作。

下文的「组织仍准入」就是这个值。不要把它读成 `ACTIVE`，也不要读成审核通过。

## 3. 三个状态

2026-10-09 工程补充：首次发布必须明确核对并同意公开承办组织、联系人与联系方式；组织默认值仅用于回填，正式公开读取赛事 contact_snapshot，不跟随组织后续修改。恢复公开沿用原快照，历史没有快照的联系信息显示待补，不自动背书旧确认。费用预览保留未配置项目，其金额/方式为 null；存在未配置项目不能发布。AI 建立的候选项目必须先人工配置免费或收费。已发布一般更正及留摘要仍按后文规则接续，不以冻结快照代替该能力。

### 发布状态

`draft` 草稿。`published` 已发布。`offline` 曾经公开，现在由组织方下架。

```text
draft → published → offline → published
```

已有报名只允许不改变承诺的一般更正并留摘要/公开依据，不改报名快照。重大改期/场地/规则/收费退改变化后置，确需调整取消旧赛事另建，不能迁移旧名单/付款。发布态一般更正的接口/版本由开发设计，不以要求先下架造成进行中联系更正死路；保存不自动改变发布状态。

草稿和正常下架可按无正式历史/有正式历史边界编辑；已取消仅历史及收尾，不通过编辑恢复。已结束不得改时间复活。

### 举办状态

`normal` 或 `cancelled`。取消后不能改回 `normal`。

真实曾发布的正常赛事，包括已下架，在未结束时可明确取消；草稿、已取消、已结束不可取消，进行中可取消。

原已发布取消保持公开并标取消；原已下架取消不能借取消动作自动公开，参与者从本人报名看到状态。取消与公开状态分开，取消不能恢复正常或继续下架/发布。停止新报名、审核通过及现场执行/新证明，保留历史，名额停用且有效统计排除；真实资金和通知可人工收尾，不自动退款。

取消原因可空。有内容时出现在公开详情里。取消前要二次确认。

### 时间阶段

不入库为可手改状态。用北京时间，按提交到服务端的那一刻计算。下架、取消和组织状态都不冻结阶段。

时间必须满足：报名开始早于报名结束，报名结束不晚于开赛，开赛早于结束。边界落在后一个阶段。

| 条件 | 阶段 |
| --- | --- |
| 当前时间早于报名开始 | `pre_registration` |
| 已到报名开始，尚未到报名结束 | `registration` |
| 已到报名结束，尚未开赛 | `registration_closed` |
| 已开赛，尚未结束 | `ongoing` |
| 已到或已过结束时间 | `finished` |

## 4. 实际是否公开

```text
可见 = 发布状态为 published 且组织状态为 certified
```

举办状态不决定能不能看见。已取消且组织仍准入的赛事仍可见，并显示已取消。草稿和已下架不公开。组织不是 `certified` 时，已发布的赛事从公开列表和详情消失，发布状态仍保持 `published`。组织以后再回到 `certified` 时，这些已发布赛事自动重新可见，不必再点发布。已下架的赛事不会因为组织回到 `certified` 而自动公开。

本期没有把组织改出 `certified` 的页面。规则先按这个判断写上，避免和审核语义混在一起。

## 5. 公开查询

公开列表和详情是专用接口。

服务在这个接口里显式跨租户读取赛事，然后强制加上第 4 节的可见条件。调用方不能靠省略租户号来查全部。租户号为空时，现有拦截器不会加租户条件。技术租户 `900001` 也不是公开范围，用它会一条都查不到。

组织内的创建、编辑、发布、下架和取消仍走该组织的管理会话，只读写这个组织租户里的赛事。

## 6. 新建、编辑和发布

新建羽毛球赛事后，发布状态为 `draft`，举办状态为 `normal`。草稿可以缺项。

发布可以把 `draft` 或 `offline` 变成 `published`。不进入人工审核。重新发布要重新做完下面的检查，不沿用上一次已经发布过的结论。同一幂等键重复提交返回同一次发布结果，不产生第二笔发布。

发布必须同时满足：

1. 操作者对该组织持有有效的 `organize` 授权。
2. 组织状态为 `certified`。
3. 举办状态为 `normal`。
4. 运动是羽毛球。
5. 第 7 节的公开字段齐全。
6. 时间关系合法。
7. 首次发布限开赛前；恢复要求真实发布历史且当前正常下架、未取消未结束，允许 `ongoing`，不重开报名或改变名单/资金。

进行中只允许符合条件的恢复，不允许草稿首次发布；已结束/取消不可发布或恢复，不能改结束时间绕过。失败保持原状态并说明原因。

## 7. 公开字段

发布时必填，并在公开页展示：

| 字段 | 本期存法 |
| --- | --- |
| 赛事名称 | 赛事上的文字 |
| 报名开始、报名结束 | 有时区时间。阶段按这里计算。是否接受报名见《报名业务流程》，窗口不搬到竞赛单元 |
| 开赛、结束 | 有时区时间 |
| 比赛地点 | 赛事上的文字。不引用场馆模块 |
| 赛事项目 | 赛事上的文字。公开页不建竞赛单元。可报名的项目在报名审核里建立，见《报名业务流程》 |
| 收费方式、整单报价及退改说明 | 从竞赛单元有效收费版本同源公开；报名冻结适用依据，不再手填另一套金额。收费项目无有效配置或二维码方式无确认可用图不开放报名 |
| 责任主体和赛事联系信息 | 所属组织为责任主体，默认组织联系信息可按赛事调整，发布前确认公开并保存快照；组织变化不覆盖旧赛事 |

公开页还展示当前阶段、举办状态，以及取消原因（如果有）。不展示租户、内部备注、操作记录、组织申请审核记录和管理人员信息。

## 8. 下架

已发布、举办状态为 `normal`，且阶段仍是报名前、报名中或报名已截止时，组织方可以下架。下架前要二次确认。

成功后发布状态变为 `offline`，公开接口立即不可见，组织内可以再编辑。举办状态和阶段不改。

已开赛或已结束不能下架。是否允许下架，以服务端收到请求时的阶段为准，不以打开页面时的阶段为准。

## 9. 本期不做

下面这些不由本流程实现。报名、收费、录分已经在后面的暂停点开发，规则以那些文档为准。

- 报名、名额、名单。见《报名业务流程》。
- 付款、到账、退款。见《收费业务流程》。公开页上的收费说明仍不产生应付金额。
- 成绩、证书。见《录分报到和证书业务流程》。
- 非羽毛球的编辑和公开。
- 赛事发布的人工审核，以及平台强制下架。
- 已发布直接修改、定时发布、取消后恢复、已结束后取消。
- 多人同时编辑、阶段的实时推送。
- 场馆、规则版本。竞赛单元见《报名业务流程》。收费版本见《收费业务流程》。

TC01 仍待业务验收。本期的对应规则是：组织不是 `certified` 时不能发布，已发布的赛事也不再公开。

## 10. 不变量

1. 赛事属于组织。
2. 发布状态、举办状态、时间阶段彼此独立。
3. 阶段只按北京时间计算。
4. 已有报名只允许一般更正，重大变更后置，当前资料不覆盖旧依据。
5. 下架后的保存不会自动公开。
6. 重新发布要重新校验。
7. 开赛后禁止首次发布和下架，但有历史的正常下架未结束赛事可恢复；结束不可恢复/取消，进行中可取消。
8. 取消不可恢复。
9. 草稿不可取消；真实曾发布的正常下架赛事未结束可取消。
10. 取消不是下架。
11. 已取消本身不使赛事不可见。
12. 组织不是 `certified` 时，已发布赛事实际不可见，发布状态不变。
13. 组织回到 `certified` 后，仍为已发布的赛事自动可见。
14. 限制以服务端执行时的状态为准。
15. 发布请求按幂等键返回同一次结果。

16. 取消必须可靠关联最小站内信＋短信任务，收件范围固定并去重，失败不回滚取消，消息不伪造退款事实。

## 2026-10-12 审核赛事排序及收费草稿删除接口

依据[ADR-045](../03-architecture/ADR-045-悬浮办赛表单与收费草稿删除.md)。`GET /sports/b/events` 与报名审核页的 `GET /sports/b/registrations/events` 按 `create_time DESC, id DESC` 返回，最新创建赛事优先。同一赛事的时间阶段、报名审核方式和公开状态仍分别判断。政府主办方管理的赛事数是汇总，不新增逐场政府发布审批。

`POST /sports/b/events/{eventId}/delete-draft` 由当前组织管理会话办理，只允许所属租户、组织的未发布正常草稿。取赛事行锁后重新核验归属及状态；发布办理命令、正式报名锁、任何状态的报名记录、名额占用、报名采集值或付款义务历史均拒绝。已发布、下架、取消赛事不按草稿删除，撤回或资金净额为零不清除既有历史。

未被报名或义务使用的收费配置属于可清理的草稿内容：单纯设置每单100元、免费版本或赛事收款方式不阻止删除。项目侧先核验报名、名额和采集值，再通过 `FeeApi.discardUnusedDraftPricing(tenantId,eventId)` 由资金侧持有同一赛事锁，复验租户、草稿状态、正式报名锁、全部价格版本对应的报名及义务历史；只删除未用价格版本（含已停用版本）和赛事收款配置。

价格及收款配置先清理，再删除空采集项、名额和项目、宣传关联，解除关联任务的赛事结果并标为 `ABANDONED`，最后删除赛事。所有步骤在删除赛事的同一数据库事务内，清理或最终删除失败全部回滚。不得删除付款义务、到账、冲正、退款、异常或正式报名事实，不办理退款。受外键保护的其他历史依赖仍可使删除失败，不放宽数据库约束强行删除。

已创建赛事的删除不直接删除对象存储原件或二维码图片，未引用文件沿用既有授权清理和保留规则。未形成赛事的AI任务继续走原 `abandon` 资料处理入口。本人报名草稿的 `DELETE /sports/c/registrations/{registrationId}` 按 ADR-023 保持从未提交及当前办理人等边界，本次赛事配置删除不放宽该接口。

上述契约取代 ADR-006 旧“有收费版本即拒绝删除办赛草稿”的条件；不把文档同步、候选保存或模拟记录作为正式一期接受证据。

## 2026-10-12 同草稿聊天修改与发布

资料创建赛事后，AI 任务仍关联原赛事；真实状态为未发布且无发布/报名历史时，可通过同一聊天持续修改名称、地点、时间、公开资料、原项目容量与价格。候选更新与实际保存分别显示；“保存修改”及表单保存按任务和赛事版本核对、组织权限与业务事务同步原对象，项目 ID 保持。其他页面已改动时拒绝覆盖并提示重新核对，已经发布后不继续使用专用草稿编辑。

“读取赛事当前内容”或明确“重新读取赛事草稿”采用同一 eventId 当前已保存的赛事、项目和费用作为新候选基线。服务端在赛事行锁内重新核验组织、未用草稿条件及任务版本；读取只更新任务候选，不写赛事。原始资料和上一候选保留，表单另保留刷新前未保存填写供展开对照及回填；回填仍需保存，项目目录已变化时不整体覆盖新目录。旧版 `CREATED` 没有可靠赛事版本／项目费用基线时，必须先显式读取再继续修改，普通任务 GET 或恢复会话不表示同意采用外部变更。其后保存继续更新原赛事及原项目，版本或费用目录变化仍拒绝静默覆盖。

“发布赛事”先保存当前修改，再在聊天内展示实际公开资料及项目费用；第一次“确认发布”若尚未显示核对卡，先展示。卡片显示后，明确输入“确认发布”与点击“确认发布赛事”使用同一正式发布服务，公开联系人同意含义可见。资料发生变化重新核对；缺收款渠道、公开字段或其他门槛仍按原服务拒绝，不显示假成功。正式发布成功显示实际赛事编号，刷新恢复同一已发布赛事。决定与具体边界见 ADR-045，实测见本轮专项报告。

聊天核对卡保存实际任务版本以及费用预览返回的 `eventVersion`、`previewHash`，确认前再次读取实际资料；未保存修改、未同步候选、版本或核对内容变化时更新卡片并清除同意，需按新内容重新确认。聊天发布请求将已核对版本和摘要作为 `expectedVersion`、`expectedPreviewHash` 携带；发布事务取得赛事行锁后重新生成当前预览并比较（CAS），差异以 409 拒绝，避免核对后又被其他页面改动的内容直接公开。既有兼容调用保留原门槛及可选参数，成功恢复仍以同一赛事真实 `published` 为准，发布幂等键继续生效。此处记录接口与交互契约，不替代本轮统一构建和普通角色实测结论。

收费赛事没有收款渠道时，可在聊天核对卡填写线下付款说明并保存，沿用实际收款配置权限及 `revision`。保存保留全部原渠道，不确认到账、不自动发布；完成后重新核对实际说明并再次明确确认。名称按正式模型固定“线下付款”。实际收款配置版本纳入 `previewHash`，说明发生变化但渠道仍可用时，旧发布核对同样失效。免费赛事不依赖收款设置读取权限；原报名后锁定等业务保护保持。
