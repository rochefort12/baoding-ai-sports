# ADR-002 一期赛事切片

2026-10-06 收口依据：[ADR-011](ADR-011-一期业务收口与交付边界.md)。本文件的“已落地”仅指历史主链代码；最新补齐/变更仍待实现及普通角色验收。一期交付称“羽毛球 M1 受控试运行业务闭环”，不等于母版全域本期或 G4；历史 10 月 8 日目标不作当前完成承诺。

日期：2026-10-03。状态：已接受。M1.1 已按 ADR-003 落地。M1.2 分两段：平台会话、组织与资质。平台会话见 ADR-005，组织申请见 ADR-004。M1.3 赛事公开见 ADR-006。M1.4 报名见 ADR-007。M1.5 长期队伍见 ADR-008。M1.6 收费记账见 ADR-009。M1.7 录分、报到和证书见 ADR-010。内部基线名称仍是「保定体育综合服务平台」；「保定市智能体育协同网络平台」只作代号。

## 决定

10 月 8 日内部目标仍是羽毛球主链，但开发按七个暂停点推进。每一段做完就停，页面实测通过后再开下一段。超级管理员只做组织申请审核。同一注册用户可以参赛，也可以申请办赛；通过和拒绝必须用超级管理员账号。数据继续使用已落库的 V001，不改写已应用迁移。

入口不另起前端仓库。超级管理员使用现有管理布局。参赛者登录后使用同一工程里的用户页面，并从那里进入「我要办赛」。普通用户登录不选择租户。体育局不建第三个入口。

组织状态 `certified` 只表示平台已准入、已开放办赛，不表示资质已经审核。承办方发布不逐场复审。对外只返回赛事公开页。规则见 ADR-006。成绩证明只给本人和该赛事承办工作人员。证书记在 `asp_honor`，类别 `event`，表示本场成绩证明，不表示官方等级。临时组队不写 `asp_team`。断网后续办使用报到和录分的 `request_key`，同一键再次提交返回原事实。

产品内 AI、场馆占用、自动抽签编排、晋级排名、申诉改判、平台代收、比分直播、志愿者、观赛者、商业订场、约战、培训、票务、商城、钱包、群聊、推荐和旧数据迁移不进入这些暂停点。

## 模块

业务模块放在 `backend/ruoyi-modules/`，由 `ruoyi-admin` 组装。模块之间只通过 `aisports-api` 调用，禁止引用其他模块的 Mapper 或实体。契约随实际调用增加，不先把 76 张表都包成接口。

| 模块 | 责任 | 首次进入 |
| --- | --- | --- |
| identity | 独立本人必要基础档案、真实短信恢复及账号生命周期；不新增通用 profile 扩展页面。sys_user 不是参赛人 | M1.1 补齐待验收 |
| organization | 承办组织、资质版本、员工授权 | M1.2 |
| event | 羽毛球赛事的草稿、发布、下架、取消和公开页。地点、项目、收费说明是公开文字。竞赛单元、规则版本和费用版本不在 M1.3。见 ADR-006 | M1.3 |
| registration | 本人报名；双打和队伍成员必须已是独立用户。名额、资格审核和名单版本。见 ADR-007 | M1.4 |
| team | 长期队伍、申请、邀请、当前成员。历史名单不在这里改 | M1.5 |
| finance | 免费、承办方收款、线下核实。平台代收不在此实现 | M1.6 |
| competition | 手工场次、报到、逐场与批量录分、一次成绩证明 | M1.7 |
| venue | 场馆、场地、赛事占用。不含商业订场 | M2 |
| scheduling | 抽签、编排、晋级、排名。未知规则不猜测算法 | M3 |
| notification | 最小站内信＋短信一期必做，先赛事取消；小程序及完整消息平台后置 | M1 补齐 |
| governance | 投诉、审计、幂等记录 | 随对应业务段 |

`aisports-mcp` 保持关闭。身份提供「是否本人且档案已齐」，组织提供「是否已平台准入（`certified`）、是否有该动作授权」，赛事提供「按可见性过滤的公开页」，队伍提供「当前有效成员和当前队长」，报名提供「有效名单」，费用提供「开立义务和确认到账」。

## 暂停点

1. **M1.1 身份。** 以 ADR-003 和《参赛者身份业务流程》为准。每名参赛者独立注册并只建立自己的档案。同名是两个账号。不建监护、不代报、不为别人建档。跨项目资料走属性目录。评测通过后再开发。此时没有组织、赛事、队伍、报名和成绩。已上线的旧身份页面不能作为本段验收。
2. **M1.2 组织与资质。** 两段都已落地，待普通用户和超级管理员分别验收。发布赛事见已开发的 M1.3。
   - **平台会话。** 以 ADR-005 的登录部分为准。注册、登录和身份档案仍按 M1.1 的页面走。登录号是平台账号，Token 带技术租户。
   - **组织与资质。** 以 ADR-004 为准。登录后申请办赛，超级管理员通过后才建组织租户并给提交人授权。其他人不能点通过。
3. **M1.3 赛事公开。** 以 ADR-006 和《赛事公开业务流程》为准。只有羽毛球可公开。组织不是 `certified` 时不能发布，已发布的赛事也不再公开。`certified` 只表示平台准入。公开页只显示名称、时间、地点、项目和收费方式。公开页上的收费说明只展示，不产生应付金额；应付金额见已开发的 M1.6。已结束不能取消。公开列表走专用查询，显式跨租户并强制可见性过滤。报名见已开发的 M1.4。代码已落地，待业务验收。
4. **M1.4 报名。** 本人及成员填写确认、正式提交冻结名单/费用并占整单名额。收费实际足额收款才可通过，付款不等待通过；赛事可无需审核（免费提交成功，收费到账重验后成功），首次正式提交锁定。已通过按截止前无人报到/无场次等限制整单撤回，新版本重提新义务不抵扣。字段链、并发和幂等修复待实现/验收。
5. **M1.5 长期队伍。** 以 ADR-008 和《长期队伍业务流程》为准。申请要队长同意，邀请要本人接受。一人可以加入多队。代表队伍报名时只取当前有效成员。退队不撤销已提交的报名。临时双打仍然不建长期队。代码已落地，待队员和队长验收。
6. **M1.6 收费记账。** 正式提交开立独立义务，免费无虚构付款；用户声明与承办方实际收款分开。人工审核仍需办赛人员操作，无需审核收费分支到账重验自动通过。报名详情提供必要人工收款/补款/冲正/退款记录，不建设财务系统，真实图、同源报价和冻结退改依据待补齐。
7. **M1.7 录分、报到和证书。** 以 ADR-010 和《录分报到和证书业务流程》为准。承办方手工建场次，不抽签，也不为手工场次制造竞赛规则。逐场录入和批量导入写入同一结果。正式结果本期不改。同一请求键不产生第二笔报到或成绩。获奖按冻结名单投影到个人证明，并能追溯同一条报名获奖。获奖人能看到自己的证明，公开页和无关账号看不到。代码已落地，待承办方和获奖人验收。

## 后续里程碑

- **M2：** venue 与平台内时间冲突。赛程只能引用已确认资源。
- **M3：** scheduling。输入是已冻结的有效名单和已确认规则。排不开时说明原因。其他运动要等规则验证后才打开自动能力。
- **M4：** 申诉和结果新版本。改判后检查后续对阵、排名和已发成绩证明。M1.7 的证明保持一次发放，直到这一段完成。
- **M5：** 平台代收和服务费。收款主体和费率另定后再做。志愿者、观赛者视进度再开。

## 验证边界

某一段只记录它真正跑过的场景。普通角色走完对应路径之前，TC 保持待业务验收。超级管理员审核资质不能代替承办方发布或参赛者报名。

费用契约在收费模块实现后，才表示已经产生的义务和已经确认的到账。队伍契约在队伍模块实现后，才表示当前有效成员。名单在报名模块实现后，才表示已通过审核的名单。不能把草案接口当成已完成。
