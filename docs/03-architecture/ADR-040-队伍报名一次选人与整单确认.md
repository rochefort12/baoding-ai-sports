# ADR-040：队伍报名一次选人与整单确认

日期：2026-10-12。依据：用户第 7 项简化对客报名交互的要求，接续 ADR-011、ADR-029、ADR-038。实际验证见本轮报告。

## 问题和决定

原队伍入口只建空草稿，用户还要在详情中逐一添加成员。页面无条件读取本人赛事采集项，队长不在本次上场名单时会收到“你不在这条报名里”。成员是否本人也沿用原创建者标记，移交办理后容易误识别。

点击报名先弹出报名方式与队伍选择。队长可查看其有权办理的有效队伍，选队后显示当前全部成员。人数适合本项目时预选可用成员；队伍人数超出项目人数时只预选本人，要求明确选择实际上场名单。不能默选其他队员凑满人数。账号或档案不齐的成员显示不可选；团队全部成员不等于本项目实际上场名单。队长可不参赛。

下一步弹窗核对队伍、项目、本次全部参赛成员和费用；确认后一次创建草稿并带入名单。本人使用现有档案快照，其他成员仍为待本人确认，站内信提供私人邀请入口。本人资料、参赛声明及赛事采集项要求不被队长或 AI 替代；不复制其他赛事答案。全员完成后，正式提交另有整单确认弹窗，再次列出完整名单、状态与费用。正式提交仍由服务端冻结资料、占名额并建立本次付款义务。

无其他成员需要确认的个人报名保留原快捷草稿入口；已有队伍空草稿可从同一选人弹窗一次补齐。已有非空名单不会被新创建请求静默替换。详情的调整成员入口折叠，作为修改而非首次报名的必经步骤。队长不在名单时不请求本人赛事采集项或本人声明接口，避免误报权限问题；成员行的 selfMember 投影以当前登录账号为准，原数据库标记保留。

## 服务端与一致性

POST /sports/c/registrations 保留 unitId、requestKey、teamId；新增可选 memberAccountIds（Long 字符串数组）。只有有效队伍当前队长可使用，必须是本队当前有效且账号、资料可用的成员，名单去重、人数与项目边界一致。未传新字段保持旧 API 草稿行为；个人请求带入成员名单被拒绝。

准备名单按 team → capacity 的现有锁顺序办理。名单、站内邀请与 prepare_team_roster 幂等回执在同一事务写入，任一成员失败全单回滚。沿用现有 asp_idempotency，payload_hash 包含项目、队伍和排序后的账号集合，result_reference 绑定报名编号。相同键改变名单拒绝；相同键重复返回当前报名，不能恢复被移除成员或把已提交/撤回状态重置为草稿。两份不同名单并发只能建立一份完整报名，另一份收到冲突。

已有空草稿只补齐，不重复建立报名；非空名单不同则拒绝并指引回详情调整。正式提交、成员本人确认、组织隔离、窗口、资金、容量和名单快照的既有校验继续生效。不新增表或重写已应用迁移，不增加表工程互依。

## 交付边界

本轮验证使用独立普通角色和标注模拟的本地赛事，覆盖队长不参赛、桌面和手机报名、邀请确认、正式提交、旧空草稿、非法成员、重复和并发。截图中原用户队伍及报名不由测试脚本代为变更。真实短信和用户亲试继续按一期清单验收。
