# ADR-015 通用 AI 内核与从资料创建赛事

日期：2026-10-08。状态：用户已确认方案，本轮按此实现首个场景。

## 决定

采用通用 AI 内核，按「场景 + 业务对象」组织。首个场景是 `event.create_from_document`，业务对象是 `event`。后续场景复用同一套模型接入、工具循环和任务记录，不另写一套模型客户端。

这不是完整 Agent 平台，也不是赛事专用 AI 内核。产品侧只增加「从资料创建」这一条办赛入口，原来的「新建赛事」保留。

## 职责

| 部分 | 负责 | 不负责 |
| --- | --- | --- |
| Node.js `ai-gateway` | 百炼兼容模式调用、视觉与 OCR、工具循环、场景提示和工具清单 | 登录令牌、业务事务、直接写赛事表 |
| Java 赛事模块 | 文件、任务、权限、限额、确认时的赛事草稿事务 | 在 Java 里请求大模型，引入 Spring AI 作为模型网关 |
| `aisports-api` | `StoredObjectApi` 的资料用途、免费项目入口、只读校验契约 | Mapper、实体、SQL |
| 报名模块 | 在调用方事务内建立免费竞赛项目，并写入金额 0、方式 `free` | 自己决定发布或收款码 |
| 现有 MCP | 在 MCP 开启时暴露读取约束、读取原文块、校验候选方案 | 发布、取消、退款、确认到账、任意写表 |

模型不持有登录令牌。网关回调 Java 时只带内部令牌和任务编号。文档正文放在不可信数据块里，不能改系统提示或工具清单。

## 数据

新增 `asp_ai_task`、`asp_ai_task_file`、`asp_ai_invocation`，迁移为 V022。任务状态为 `UPLOADED / PROCESSING / PENDING_CONFIRMATION / CREATED / FAILED / ABANDONED`。

原始文件用途是 `ai-source`，不借用收款码用途。解析和模型调用不占着数据库事务；用户确认时，赛事草稿、免费项目和任务状态在同一个业务事务里提交。同一任务再次确认返回已经创建的赛事。

## 降级

密钥为空时不请求外部模型。docx、xlsx 和文字版 PDF 仍本地解析，人可以改完再创建草稿。图片和扫描版 PDF 保留文件，状态为失败，配置密钥后可以重试。

上传前必须同意把资料发往百炼。一次最多 8 张图片，扫描 PDF 最多 15 页，每组织每日新建任务默认 20。这些上限来自环境配置。旧版 doc 按文件内容拒绝。

被取代：上面「一次最多 8 张图片」见下一节。扫描 PDF 页数和每日次数仍保留。

## 尚未验证

本轮没有配置百炼密钥，没有对真实模型发过请求。网关里的兼容模式调用、OCR 模型 `qwen3.5-ocr` 和视觉补识别路径已经写好，等密钥配置后再做真实调用验收。

被取代：上面「没有配置密钥、没有对真实模型发过请求」见下一节。`qwen3.5-ocr` 仍未验证。

## 2026-10-08 规程照片实测

密钥和 `qwen3.8-flash` 已配置。页面上传由照片本地整理的 Word 时不请求模型，确认出草稿 `2108143243026771970`。上传 8 张规程正文照片时请求视觉模型，确认出草稿 `2108153397713674242`。13 张照片被 8 张上限拒绝。

模型提交 `validate_event_proposal` 且名称非空时，网关收下该候选，允许字段是扁平字符串。Java 等待 290 秒，网关中止 300 秒。扫描 PDF 仍先调用 `qwen3.5-ocr`，这一步还没有真实响应。

## 2026-10-08 放开图片张数

图片不再按张数拒绝。单张仍不超过 15MB，整次请求仍不超过 40MB。扫描 PDF 仍最多 15 页。JPG、PNG、WebP 直接交给视觉模型 `qwen3.8-flash`。`qwen3.5-ocr` 只在扫描版 PDF 的页面上调用，规程照片那次没有走到这条路径。

## 2026-10-08 确认时由人回答问题

能确定的字段由助手直接记下。多种写法、缺失的审核方式、已过去的比赛时间、没有单列的名额，以及被整句误识别的项目，改成对话。助手一次问一处，给出可回复的说法，人也在同一个对话框里直接回答。追问、要例子、说没听懂时，把这句话交给文本模型回答，不把原问题再念一遍。只有说清了决定，才写入对应字段。回复「创建」后才走原来的草稿事务。

被取代：见「2026-10-08 一轮由模型决定」。上面「一次问一处」和「回复创建才创建」不再作为当前做法。

## 2026-10-08 一轮由模型决定

办赛人的每一句都由模型结合草稿和最近对话理解。模型自己决定回答、更新草稿、追问或调用已有的读取、约束和校验工具。明确读到或说清的字段写入草稿；明确要改的字段覆盖原值；没说清就追问，不把正在问的审核方式写成已选定。`registrationReview` 只接受模型给出的 `manual` 或 `none`，Java 不把「不审核」这三个字翻译成 none。

只有对话里模型给出的行动是 create，并且原来的确认校验通过，才在同一个本地事务里建立赛事和免费项目。识别资料那一次不允许创建。对话和来源记在原有候选 JSON 里，不新加表。空的项目列表不覆盖已有项目。

## 2026-10-08 文本和视觉改为 DeepSeek-V4.1-Flash

模型 ID 用官方名称 `deepseek-flash`，兼容模式地址为 `https://api.deepseek.com`。密钥仍只放在未跟踪的 `.env`，变量名继续是 `DASHSCOPE_API_KEY`。照片和扫描页都走这一个模型，不再调用 `qwen3.5-ocr`。调用时关闭思考模式；必须交回草稿的那一轮要求 JSON。识别结果里没有赛事名称时，再要一次字段。上传前的同意文案改为发送到 DeepSeek。

## 2026-10-08 对话只改办赛人明确说的内容

咨询、补充、修改和同时说的几件事都由模型根据这一句和草稿判断。只提问时不改正在问的内容，也不逐项催填。明确修改才覆盖。规程原文、模型理解和待确认的事在回复里分开，不编规程没有的要求。回复只用业务语言；内部名字若漏出，在交给页面之前换成业务说法。

解析失败先再要一次 JSON。仍然失败时返回 `MODEL_OUTPUT_INVALID`，页面说明这一句没有处理完、草稿没有改，不用业务口吻假装已经听懂。超时和网关连不上分别说明。
