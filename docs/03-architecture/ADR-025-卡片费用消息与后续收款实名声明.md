# ADR-025 卡片、项目费用、站内信入口，以及收款、凭证、实名、声明的待实施边界

日期：2026-10-09。用户要求先完成手机赛事卡片、项目费用快捷设置和站内信入口；赛事统一收款、付款凭证、实名照片、声明网签只核对现有模型和接口并给出方案。第 6、7 项的核验方式和电子签范围本轮不认定。

2026-10-10：用户后续授权完整收费流程测试和模拟凭证上传，付款图片凭证已按 [ADR-027](ADR-027-可选付款凭证与报名资金流程验证.md)实施，并完成真实本地接口/存储验证；下文“付款凭证未实现”仅指本文原制定时状态。赛事多渠道、实名等仍按各自待办，不因此完成。

## 已按现有规则改的界面

手机公开赛事卡片在窄屏只留两行标题、比赛日期和报名状态。地点、收费说明和封面留在详情。320/390 宽不把长标题撑出屏幕。桌面宽屏卡片仍显示地点和收费说明。

竞赛项目列表和收费记账列表直接显示「未配置」「免费」或「收费 ¥金额」。未配置打开设置时不预选免费，未选择不能保存成免费。收款方式仍是现有的线下或承办方二维码，不在本轮改成赛事级多渠道。

参赛端顶栏在手机和桌面都保留「我的消息」，并显示未读数。列表、已读和赛事/邀请跳转沿用 `GET/POST /sports/c/notices`。取消赛事、入队邀请、报名成员邀请仍写 `asp_notification`；短信投递仍是 failed，原因是真实短信未接通，页面不把它写成发送成功。管理端通知公告铃铛在手机宽度也显示，它仍是 RuoYi 公告，不是上述站内信。

## 赛事统一收款（未改模型和接口）

现状：收费版本在竞赛项目上，`payment_mode` 只能是 `free`、`offline`、`organizer_qr`。提交时把金额和方式写入报名的费用快照。到账仍由承办方人工确认。没有在线支付回调。

拟按用户决定：微信、支付宝、银行转账、线下收款挂在赛事设置，可同时启用多种；项目只保留免费或收费及金额。参赛者仍自行付款，承办方仍人工确认到账。已提交报名的价格和收款依据留在原快照，不因后来改渠道而改写。

实现前要单独加迁移：赛事渠道是多值启用状态，项目价格版本不再携带渠道；新提交才读取当时启用的渠道。旧的 `offline` / `organizer_qr` 版本继续按原快照解释，不批量改成新渠道。权限仍用现有收费设置权限。事务仍是发布一版价格或改渠道各走自己的短事务，不把历史义务和到账记录放进同一次改写。

## 付款凭证（未改接口）

现状：付款声明只记声明本身。ADR-011 写明不要求、也不提供截图上传。到账确认是另一笔人工登记。

拟按用户决定：在具体报名的付款声明上可以上传、预览和补充凭证。页面文案用：「建议附上付款凭证，方便承办方核对。不上传也可以提交。上传只说明你声明已付款，还不代表承办方已经确认到账。」没有凭证不得拒绝声明。

实现时凭证是声明的附件，状态与「已声明」「已确认到账」分开。上传失败不回滚已经成功的声明。文件仍走现有对象存储和类型、大小限制。历史没有凭证的声明保持有效。本轮不改 ADR-011 的那句后置说明；落地代码时再标明被本决定取代。

## 实名与照片（规则未定，不实现）

现状：本人档案可填姓名、出生日期、性别、证件类型和证件号。`asp_person.verification_status` 已有 unverified、pending、verified、disputed，当前页面不因填了姓名或证件就把状态改成 verified。档案没有照片字段。赛事采集走组织字段目录，不是平台强制实名。

尚未决定核验方式，因此不新增「认证成功」状态流转。差异先记下：

- 人工核验：承办方或平台人员对照证件材料，把 verification_status 从 pending 改为 verified 或 disputed。事务只改核验状态和核验人、时间，不改已提交报名里的姓名证件快照。
- 第三方核验：调用外部身份服务，结果只能作为核验记录。失败、超时不等于未填写。不把第三方通过自动写成报名资格通过。

照片若以后要做，是本人档案的可选文件，赛事可按字段目录要求，平台不统一强制。填写资料和核验通过继续用两个状态表示。

## 声明文件与网签（范围未定，不实现）

现状：赛事有一段参赛声明文字和一张声明图片。已有正式报名后不能再改。没有多文件、版本号、本人阅读确认或签署记录。队长不能代替成员确认敏感字段，这条继续适用。

方案只列到待确认，不建表：

- 文件版本：每次上传新文件产生新版本，已报名的人仍指向提交时看到的版本。
- 本人阅读确认：报名成员自己确认某一版本，留下账号、时间和版本。队长不能代签。
- 签署记录与报名关联：确认记录挂在报名成员上，不挂在整单提交人。
- 被取代：见文末「2026-10-09 声明用本人点击确认」。第三方电子签章不采用。

## 2026-10-09 实名接入条件

用户要求核对接入支付宝或微信实名核验的条件。本轮只核对公开文档，不接入、不保存密钥、不把自填姓名证件写成核验通过。ADR-003「本期不接权威身份核验」仍然有效，直到真正开通并另写实现决定。

支付宝「身份证二要素核验」`datadigital.fincloud.generalsaas.twometa.check`（文档中心，2026-10-09 读取）：服务端调用，核对用户授权后传入的姓名和证件号是否一致。开通前要有支付宝开放平台应用，并签署或升级包含该产品的合约；没有授权时返回 `INVALID_SWITCH`。商户支付宝账号余额不足时返回 `ACCOUNT_MONEY_LIMIT_ERROR`。证件类型文档列出身份证、港澳居民居住证、台湾居民居住证。返回匹配或不匹配。这不覆盖本系统里的护照等其他证件，也不等于报名资格通过。另一套「支付宝身份验证」要在商家平台开通产品，并在支付宝客户端里做人脸或证照，文档写明暂不支持沙箱，也不适合当前这个网页直接调用。

微信支付「实名验证（小程序）」文档更新于 2026-08-13，页首写明该功能处于灰度、暂未开放使用。即便以后开放，也要有微信支付商户号、已绑定的小程序 AppID、商户 API 证书，并先取得该微信用户授权，再核对他的姓名和证件是否与微信支付实名一致。当前产品是网页，不是微信小程序，所以这条现在接不上。微信人脸核身另有主体和类目限制，公开说明只给法规要求实名办理的限定行业，不能当成体育办赛已可申请。

因此现在不能接入。若以后走支付宝二要素，需要开放平台应用、已签署的该产品合约、可扣费的商户账号，以及用户同意后再把姓名和证件号发去核验。核验失败或超时仍只表示没核验通过，档案里已填写的资料保持原样。

## 2026-10-09 声明用本人点击确认

用户决定免责声明、反兴奋剂声明等由本人点击确认，不接第三方电子签章。点击确认只表示该账号在当时看过并同意这一版文件，不是电子签章。队长不能代队员确认。赛事可上传文件并设定是否必须本人确认；不要求确认的文件只供阅读。已报名的人继续指向他确认过的版本，后上传的新文件不改写旧确认。确认记录挂在报名成员上，留下账号、时间和文件版本。未确认而赛事要求确认时，不能完成该成员的正式确认。本决定取代上文「站内留痕还是电子签章尚未决定」。

## 2026-10-09 本期只做资料登记

用户决定本期不做证件与姓名是否一致的核验，档案只称为资料登记，不称实名验证。支付宝、阿里云、微信的核验条件留在上文，作为后续待办，不在本期接入。

参赛声明用现有文字和图片作为这一版内容。赛事可要求成员本人点击确认。确认记下当时内容的摘要；内容变化后要重新确认。队长不能代确认。这不是电子签章。多份独立文件仍可后补，不改变本人点击确认这条规则。
