# ADR-009 收费记账

日期：2026-10-05。状态：已开发，待业务验收。迁移 V011。TC28–TC40 仍待承办方和参赛者验收。

2026-10-06 规则同步：原 V011 是历史实现基线，下列更新为已确认目标，变更尚未实现/验收。跨模块最终规则见 [ADR-011](ADR-011-一期业务收口与交付边界.md)。

本决定细化 ADR-002 的 M1.6。业务流程见 [收费业务流程](../02-modeling/收费业务流程.md)。报名边界见 [ADR-007](ADR-007-报名.md)。

## 决定

收费写在赛事所属组织的租户。费用版本继续用 `asp_fee_policy`，按竞赛单元各自编号。同一单元同时只有一条 `active`。已生效的金额和收款方式不改，改价另起一版并退役旧版。

收款方式为 `free`、`offline`、`organizer_qr`，收款主体一期是承办方。公开报价与生效收费版本同源，整单计费，公开方式、主体及人工退改依据；没有有效版本不能开放项目报名，免费必须是零金额版本。二维码方式需授权人员上传实际收款图并确认可用/主体一致，不能以模拟图或空文件开放收费报名。

报名成功进入已提交时才产生 `asp_fee_obligation`。免费记 `not_required`，不产生付款。收费记 `open`。撤回或拒绝未付款义务时改为 `void`。再次提交新插一行，不恢复旧义务。义务幂等键不复用报名请求键。

`asp_payment` 表示实际确认到账，用户声明另记。付款人账号可空，登记实际姓名/称呼、金额及时间；一期全部人工办理，不启用回调自动确认。必要多笔收款/补款、分次退款分别留事实，净有效实收达到应付才满足付款条件；少付待补、多付人工处理，不跨报名抵扣。异常和重复请求有授权、幂等、事务及金额保护，模型/契约仍需调整。

付款正式提交后即可办理，不等待审核；收费审核通过必须有效实收足额。无需审核赛事的收费分支到账后重验资格/窗口并自动通过，免费不制造到账。正常付款入口开赛或拒绝/撤回/取消关闭，真实迟到款仍登记收尾。已付款失效保留原收款，按冻结政策人工处理待退、办理中、已退或无需退款及依据；平台不发起退款，退款只登记平台外真实事实。

冲正保留原记录及审批历史，重新计算有效资金而非覆盖事实。误确认使已通过报名欠款时：无人报到暂停新报到，补足可解除付款限制；已有报到/场次人工协调，不自动清除、改判或撤证。元数据更正和实际退款不当作未到账冲正。有其他有效足额款/免费不误拦，取消等失效限制仍生效。

报名模块只通过 `FeeApi` 调用。付款权限是 `payment`，和报名审核的 `organize` 分开。开户时的初始授权同时带上这两项。

收费设置仍在竞赛项目，人工资金入口集中报名详情收费区域，简明汇总/记录和到账、退款、更正/冲正操作，不恢复完整财务菜单。用户声明可填付款人称呼、时间和备注，不上传截图，不能自动作为到账事实；成员只见应付及进度。当前模拟码/默认到账参数属未完成缺口，见一期清单。后置交互见 [收费记账后续增强](../02-modeling/收费记账后续增强.md)。

## 本期不做

平台在线收款、微信/支付宝支付集成、成员分担计价、自动退款/对账、旧付款抵扣新报名、按人数计价、服务费和结算、双人复核/复杂审批。真实补款和分次退款的必要登记属于一期，不代表建设成员分担或财务系统。`asp_fee_item`、`asp_fee_share`、`asp_service_fee`、`asp_settlement` 暂不启用。

## 2026-10-07 实施落点：人工到账请求键核对内容

同一把人工确认键再次到达时，必须仍是原来的义务、实际付款人、付款人账号、金额和到账时间，才返回原结果。换义务、付款人或时间则拒绝，并记一条付款异常，不把另一笔义务改成已结清。页面每次点击仍使用新的请求键；这里处理的是同一请求被拿去表示另一笔事实。

建立竞赛项目和第一版收费放在同一个事务。收费方式无效时项目和收费版本一起回滚。同一把请求键、同一内容再次提交返回原来的项目；内容不同则拒绝，不另插一条。页面在这次点击成功前复用请求键，表单内容变了才换新键。已有项目的「收费设置」仍单独保存下一版。

## 2026-10-07 实施落点：报名详情里的人工资金

确认到账、冲正、登记已退款和无需退款都在报名名单上，调用原来的付款接口，不另开财务菜单。待付款的收费报名显示确认到账。已结清的显示冲正。已付款报名撤回或拒绝后留下的待处理资金显示登记已退款和无需退款。这种报名即使已经回到草稿，也留在名单里，直到资金后续结束。声明付款仍然不是到账。

## 2026-10-08 实施落点：撤回后再提交

未付款义务在撤回或拒绝时改为 `void`，包括免费的 `not_required`。再次提交另记一条新义务，不把上一笔未结束义务当成这次报名的账单。已经到账的 `settled` 留在原行，并保留待处理的资金后续。
