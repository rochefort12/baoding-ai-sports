# ADR-047 业务迁移基线合并

日期：2026-10-13。依据：用户确认本机数据库可以删除重建，并要求在保证结果正确的前提下，从维护角度合并 V001–V041。此决定取代 ADR-046 里「已应用迁移不重写、checksum 不替换」对这 41 个文件的约束。ADR-046 的 Docker 试运行方式仍然有效；那个副本如果还记着旧账本，不能用新脚本直接升级。

## 决定

业务迁移改为三份脚本，按顺序执行：

1. `V001__schema_baseline.sql`：空库跑完原先 41 个版本后的业务表结构。容器初始化直接执行，文件自带事务。
2. `V002__platform_seed.sql`：相对框架初始数据新增或改写的租户、角色、菜单和套餐。收费记账菜单保持最终的停用内容。平台客户端只追加 `platform` 授权，不改写其他列。
3. `V003__catalog_seed.sql`：运动项目、比赛类型、成长规则和智能体定义。

框架 SQL 仍在业务脚本之前。旧库上的数据修补不进入这三份脚本，包括清空旧档案、改写旧队伍状态、回填报名和某一场测试赛的改名。结构变化留在基线里，例如项目名称唯一索引、退款接收人、分享邀请列。

模型源仍是 `catalog.py`。当前模型有 121 张表，基线有 118 张表、1805 列。多出的 `asp_attribute_definition`、`asp_attribute_requirement`、`asp_person_attribute` 尚未进入基线。基线补上了原先已建表、但缺注释的 26 个列，注释取自当前模型。

以后的变化从 `V004` 另写。不修改这三份已登记脚本，也不把 Flyway 放进应用启动。

## 验证

临时 PostgreSQL 17.11 中，先按旧 41 个文件得到对照库，再在空库执行三份新脚本。全部表的业务数据一致；创建和更新时间不参与比较。业务表的列名、类型、空值约束和默认值一致。检查约束和部分索引的差异只是同一条件的两种写法。`preparation.sql` 在新库通过：118 表、1805 列、列注释、租户外键、版本、状态、唯一和配额检查。`generate-model.py --check` 为 121 表、1843 列。

本轮没有删除已有数据卷，也没有把新脚本装进 `aisports-dev`、`aisports-dev-zyt`、`aisports-dev-qjl3` 或 Docker 试用库。这些库仍是旧账本，下次执行迁移前必须重建。
