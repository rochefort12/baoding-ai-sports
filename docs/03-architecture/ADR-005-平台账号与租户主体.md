# ADR-005 平台账号与租户主体

日期：2026-10-04。状态：已开发，待业务验收。平台会话和组织申请、开户、管理会话都已落地。TC 仍待业务验收。

2026-10-06 新增目标见 [ADR-011](ADR-011-一期业务收口与交付边界.md)：顶栏身份/组织切换一期必做，标签页独立会话后置；重置和关闭撤销平台及相关组织会话。注销/新注册/核验关联需分别保留旧操作者、稳定 person 和当前有效访问权，不盲目复用唯一 person_id 或 sys_user 映射；组织唯一管理人注销前须移交。新增能力仍未实现/验收。

本决定说明平台自然人、组织成员和若依租户账号如何分开。M1.2 的申请字段、审核状态和页面仍以 ADR-004 为准。

平台会话替换登录号。注册仍会在租户「平台参赛者」写一条遗留 `sys_user`，并记在 `asp_account.backend_user_id`。登录校验不再使用这条后台用户。组织申请通过后才开通组织租户，并兑换管理 Token。

## 身份

不新建名为 `platform_user` 的表。`asp_account` 就是平台账号。

| 概念 | 落点 | 权威内容 |
| --- | --- | --- |
| 平台账号 | `asp_account` | 一个自然人。没有业务租户 |
| 登录凭证 | `asp_login_identity` | 手机号、以后的微信等渠道。都指向同一个平台账号 |
| 参赛档案 | `asp_person` | 可选。没有档案也可以申请办赛 |
| 组织授权 | `asp_staff_grant` | 平台账号与组织的成员关系、动作和是否有效。这是进入组织的权威 |
| 租户主体映射 | `account_tenant_principal` | 一个平台账号在一个租户里最多一个若依用户 |
| 租户内账号 | `sys_user` | 只为若依 B 端准备的技术主体，不是平台自然人 |

`asp_account.backend_user_id` 降为遗留列。它只能指向一个 `sys_user`，继续服务当前参赛者登录，直到平台登录替换完成。新的组织关系不使用它。

`account_tenant_principal` 在开发时写入模型源。它是共享表，没有若依自动追加的租户条件，并加入 `tenant.excludes`。列至少包括 `account_id`、`tenant_id`、`sys_user_id`、`status`。这里的 `tenant_id` 记录主体属于哪个组织租户，由服务写入和查询。唯一约束是 `(account_id, tenant_id)` 和 `sys_user_id`。它不是成员授权。映射存在，不能推出这个人可以进入组织。

## 技术租户

平台 Token 必须带一个租户号。当前若依在租户号为空时，租户拦截器不加 `tenant_id` 条件，会跨租户读取。因此使用一个固定的技术租户号，让意外查询变成 `tenant_id = 该编号`，查不到业务数据。

这个租户只为兼容现有登录校验和租户拦截器。它不是业务租户，不对应组织，不表示用户身份，不存放业务数据，用户不可见，名称也不能写成「平台参赛者」或某个组织。编号不用 `000000`，也不用 `100001`。只插入 `sys_tenant` 一行，不走下面的开户流程。以后若有真正的平台范围，可以替换它，但不能把它解释成「所有 C 端用户属于这个租户」。公开赛事列表也不使用它，也不靠把租户号留空来跨租户查询。见 ADR-006。

平台登录仍走 `POST /auth/login`。一期由客户端带上这个技术租户号，使用户无感知地通过 `checkTenant`。策略只查 `asp_login_identity` 和 `asp_account`。登录号是 `platform_user:{asp_account.id}`。`sys_user.user_type` 的长度是 10，放不下 `platform_user`；这个类型只出现在 Token 的登录号上，不写入 `sys_user.user_type`。

## 两种会话

平台会话和管理会话可以同时有效。一次请求只带其中一个 Token。两边的 Header 名都可以仍叫 `Authorization`，由访问平台接口还是组织管理接口决定带哪一枚，并带上对应的 `clientid`。

| 会话 | 登录号 | 作用 |
| --- | --- | --- |
| 平台 | `platform_user:{accountId}` | 档案、组织申请、进入组织 |
| 组织管理 | `sys_user:{sysUserId}` | 该租户内的若依菜单和数据权限 |

进入组织的顺序：

1. 当前 Token 的类型必须是平台账号。
2. 读取 `asp_account`。
3. `asp_staff_grant` 对该组织有效。
4. 组织已开放办赛，租户状态正常。
5. 按账号和该组织的租户查找映射和 `sys_user`，用户状态正常。
6. 调用现有登录，签发管理 Token。

每一步都读权威数据，不把授权结果提前缓存在平台会话里。存在 `sys_user` 不能代替成员校验。

产品规则：组织管理主体不提供独立登录。只能从已认证的平台账号，经组织授权校验后进入组织工作台。密码、短信、邮箱和第三方登录碰到映射表里的 `sys_user` 一律拒绝。

## 开户

不另写一套租户初始化。`SysTenantServiceImpl.insertByBo` 继续负责租户、套餐角色、角色菜单、根部门、角色部门、字典、参数和流程同步。唯一的变化点是管理员如何产生：

- 后台手工开户：仍用用户名和密码。
- 组织审批通过：为指定的 `asp_account` 创建 `sys_user`，写入映射，并绑到本次开户产生的角色和部门。

开户方法返回 `tenantId`、`deptId`、`roleId`、`sysUserId`，调用方不再按名称查找。调用放在 `TenantHelper.ignore()` 里；现有的 `ignore` 在 `finally` 中恢复租户上下文。用户名由平台账号编号生成，不超过 `sys_user.user_name` 的 30 位，不使用手机号，插入前按租户内查重。`user_type` 保持 `sys_user`。

审批通过是一次开通，不是先改状态再补数据。同一数据库事务内的顺序是：

1. 申请仍为 `pending`。
2. 按上面的开户变化点创建租户和主体，拿到租户号。组织表的 `tenant_id` 不能为空，所以开户在写入组织之前。
3. 用这个租户号创建组织。
4. 写入 `asp_account_tenant_principal`。
5. 写入该申请人的 `asp_staff_grant`。
6. 最后把申请改为 `approved`。
7. 提交。

任一步失败则整笔回滚，申请保持 `pending`。`insertByBo` 现有事务传播是加入当前事务，开通方法保持同样的传播，不能单独提交。一期不增加「开通中」状态。对象存储或外部服务以后不能只靠这一笔数据库事务时，再把开通从「已通过」里拆出来。

一期一个租户只有一个组织，申请人的这份授权投影为若依租户管理员角色。该角色会跳过租户内数据权限。这只是本期的投影，不是「组织所有者永远等于租户管理员」。一个租户里有多个组织时，组织所有者不能再使用这个角色。

`asp_staff_grant` 是业务授权。`sys_user_role` 是它的若依投影。成员失效或降权后，无论旧 Token 里还有什么菜单，都不能再进入该组织。变更顺序是：先改 `asp_staff_grant`，再改角色投影，然后只注销 `sys_user:{id}` 的管理 Token。平台 Token 保留。下次进入组织时按新的授权重新兑换。

## 会话标识

多用户体系里，认证会话的查询、踢下线、注销和权限失效不能只拿数值 `userId`。必须使用完整登录号 `userType:userId`，或同时匹配用户类型和用户号。

`SysRoleServiceImpl.cleanOnlineUser` 只比较 `LoginUser.userId`。用它清理组织主体时，可能误踢用户号相同的平台会话。组织授权变更改为按 `sys_user:{sysUserId}` 取得 Token，再逐个注销。

## 本期不做

不改 Sa-Token 的单套登录逻辑，不新增第二套 `StpLogic`。不把平台账号迁进组织租户。不在 `asp_staff_grant` 上保存 `sys_user_id`。不做一人多组织，也不做登录后切换组织。微信登录以后只增加 `asp_login_identity` 渠道，不按渠道新建平台账号。

## 2026-10-07 实施落点：平台密码失败计数

平台登录在密码核对前走与后台密码登录相同的 `checkLogin`。计数键落在技术租户 `900001`，不和某个组织租户的后台用户混用。未绑定或已停用的手机号仍只返回「手机号或密码错误」，不写入失败次数。已绑定账号连续错误达到配置次数后锁定；锁定期间正确密码也不能登录。登录成功会清掉这次计数。图形验证码失败仍只记登录失败，不计入这把密码锁。
