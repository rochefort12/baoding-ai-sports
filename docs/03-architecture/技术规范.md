## 互斥锁

名额抢占不使用数据库行锁排队。业务代码依赖 `MutualLock`，不直接选择客户端。

| 实现 | 何时启用 | 行为 |
| --- | --- | --- |
| `LocalMutualLock` | `aisports.lock.mode` 缺省或为 `local` | 当前进程内的可重入锁 |
| `RedissonMutualLock` | `aisports.lock.mode=redis` | Redis 锁。客户端是已有的 Redisson，不使用 Jedis、Lettuce 或 RedisTemplate |

配置在 `application.yml`。当前值是 `local`。改成 `redis` 后，同一个 `MutualLock` 注入点换成 Redis 实现，业务调用不用改。

Redis 键前缀是 `aisports:lock:`。Redis 实现必须给出持有上限，进程异常退出后由租约释放。单机实现把锁留到方法结束，忽略持有上限。

等待超时或被中断时，动作不会执行。

上游若依已经引入 Lock4j，默认执行器就是 Redisson。名额、重复报名这类互斥不要直接使用 `@Lock4j` 或 `LockTemplate`，否则会绕过当前的单机默认。Lock4j 继续只服务上游原有调用。

名额键按竞赛单元区分，例如 `capacity:{tenantId}:{unitId}`。报名提交、撤回、通过、拒绝，以及邀请、加入队员、移除成员、确认邀请和拒绝邀请都走这把锁。代表队伍先取 `team:{teamId}`，再取容量锁。同一人在同一单元的有效报名仍要靠数据库唯一约束挡住锁外的重复写入。`asp_capacity_pool.used_count` 的上限检查继续保留，作为结构防线，不负责排队。

单机锁不能保护多个应用实例。出现多实例时，把模式改为 `redis`，并确认各实例连的是同一套 Redis。

## 最新规则的实现要求（待落实）

成员变更和提交冻结已共用容量锁，并在锁内重读后再写。合法撤回、重提的请求键已按 `asp_registration_submit_key` 区分旧重放和新提交。容量调整尚未实现，以后必须使用同一把容量锁，数据库事务和约束仍是权威，Redis 锁不代替一致性。付款足额判断、审核通过/自动通过、冲正报到限制及取消并发须按当前义务、提交版本和赛事状态重新校验，不使用页面旧状态或回调直接改资格。

资金各笔事实与声明分开，请求键绑定规范化操作内容，重复键不同内容拒绝；退款累计/冲正金额保护在事务内执行。目录组织归属、赛事配置/确认版本与名单快照分开，上传实际类型/5 MB/引用保护和未引用 7 天清理并发检查。

最小通知复用框架界面/适配，持久业务收件、服务端已读、outbox、有限重试及回执需要补齐。平台账号收件键不能混用后台 userId，身份切换清理权限/缓存/异步响应/推送上下文。重置/注销撤销相关组织会话。各模块经公开 API 协作，不跨模块直用 Mapper；不引入完整财务、规则、消息或工单平台。
